# Repository Guidelines

## Project Structure & Module Organization
- `apps/` holds deployable applications (frontend Angular, backend Effect-TS). Each app typically contains `src/`, config, and project-specific tests.
- `libs/` contains shared libraries used across apps; keep APIs stable and avoid cross-boundary imports that violate Nx module constraints.
- `tools/` contains shared build/deploy tooling (including Nx executors).
- `docs/` stores longer-form documentation.
- `dist/` is build output (generated by Nx); don’t edit by hand.

## Build, Test, and Development Commands
- `pnpm run lint:affected` lints all affected projects.
- `pnpm run test:affected` runs affected unit tests.
- `pnpm run build:affected` builds affected projects (and storybook where configured).
- Use `pnpm exec nx <target> <project>` for project-scoped tasks, e.g., `pnpm exec nx test user-flow-manager`.

## CI/CD Execution Policy
- All CI/CD operations must run via Nx targets (`pnpm exec nx ...`), including deployment workflows.
- CI/CD deployment/release logic must be implemented as Nx executors (for example under `tools/`), not standalone scripts.
- Do not use `nx:run-commands` + script wrappers for CI/CD deployment/release targets.
- Do not invoke raw `node`, `docker`, or `aws` commands directly in CI/CD jobs; call the appropriate Nx executor-backed target instead.

## Coding Style & Naming Conventions
- Indentation: 2 spaces; max line length 120.
- Prettier is the source of truth (`.prettierrc`); use single quotes and trailing commas.
- ESLint enforces Nx module boundaries; avoid importing across disallowed library boundaries.
- SCSS is the default style language for Angular generators.

## UI and Design System
- App Speed follows Material Design 3. **All UI comes from the shared library `libs/ui`** — see `docs/conventions/design-system.md` and `docs/adr/ADR-0008-shared-design-system.md`.
- Every visual value is a theme token: `--mat-sys-*` for colour roles, type, shape, elevation and state; `--ui-*` for spacing, motion, status colour and layout. Never write a literal colour, pixel radius, `box-shadow`, font size or breakpoint in a feature.
- Use Angular Material for standard controls and do not restyle them. Use `@app-speed/ui/*` for shared patterns.
- If a token or component is missing, add it to `libs/ui` with a story first, then use it. When the same markup appears in a second feature, move it into `libs/ui`.
- The Storybook in `apps/design-system` (Foundations, Material, Components) is the reference; read the relevant page before building or changing UI, and add or update stories with the change.
- `app-speed/no-hardcoded-colors` reports literal colours in component styles. Disable it only for artwork or canvas exports, with a comment explaining why.

## Angular Agent Guidance
- This workspace expects the Codex skills `angular-developer` and `angular-new-app` from `angular/skills` to be available locally.
- Use `angular-developer` for Angular work in `apps/portal`, `libs/ui/**`, and Angular libraries under `libs/audit/**`.
- Use `angular-new-app` only when creating a brand-new Angular app or standalone Angular workspace.
- In this Nx monorepo, prefer Nx-aware commands for generation and verification: use `pnpm exec nx ...` targets for build, test, lint, and other project checks instead of raw `ng build` for existing projects.
- When scaffolding Angular code, prefer workspace-consistent generators and keep outputs inside the owning Nx project boundary.
- For Angular secondary entry points and public APIs, export only symbols consumed outside the defining file or entry point; keep helper/base types file-local when only used to build exported aliases.

## Learning more about Effect

This repository uses the Effect Typescript library.

Before writing any Effect code, first read `node_modules/effect/AGENTS.md`
**completely**, and follow the links in the file when required.

If you need to learn more about particular Effect apis and concepts that the
guide doesn't cover, search through the source code in `node_modules/effect/src`.

## Testing Guidelines
- Unit tests use Vitest (Nx + Vite setup).
- E2E tests are set up with Cypress (run via Nx targets).
- Name tests `*.spec.ts`/`*.test.ts` and keep them near the source when practical.
- Run CI-style coverage with `pnpm exec nx test <project> --configuration=ci` (when the target is configured).

## Commit & Pull Request Guidelines
- Commit messages must follow Conventional Commits (Angular preset), e.g., `feat(ui): add audit status badge`.
- Husky/commitlint will block non-compliant commits.
- PRs should include a clear summary, testing notes (what you ran), and screenshots for UI changes.
- CI runs lint/test/build on PRs; keep changes scoped so `nx affected` remains fast.

## Security & Configuration Tips
- Keep secrets out of the repo; use environment variables and local `.env` overrides.
- Deployment and CI are managed via GitHub Actions; avoid direct edits to `dist/` artifacts.

## Source Code Reference

Source code for dependencies is available in `opensrc/` for deeper understanding of implementation details.

See `opensrc/sources.json` for the list of available packages and their versions.

Use this source code when you need to understand how a package works internally, not just its types/interface.

### Fetching Additional Source Code

To fetch source code for a package or repository you need to understand, run:

```bash
npx opensrc <package>           # npm package (e.g., npx opensrc zod)
npx opensrc pypi:<package>      # Python package (e.g., npx opensrc pypi:requests)
npx opensrc crates:<package>    # Rust crate (e.g., npx opensrc crates:serde)
npx opensrc <owner>/<repo>      # GitHub repo (e.g., npx opensrc vercel/ai)
```
